# CONVENTIONS — 这个仓库的约定

> 归属与跑法见仓库根的 [`AGENTS.md`](../AGENTS.md)。本文只写「怎么写」。

## 语言

提交信息、文档、代码注释一律中文。标识符、文件名、目录名用英文。

## AGENTS.md 与 CLAUDE.md

**只有一份内容。** `AGENTS.md` 是真文件（Codex 与 Claude Code 都读），
`CLAUDE.md` 是指向它的符号链接。不要写成两份——两份必然分叉，
而分叉的须知比没有须知更糟。新增子目录须知时照此办理。

## 文档放哪

- **模块文档贴着实现放。** `backend/fanisl/knowledge/README.md`、
  `binance/README.md`、`auth/README.md` 都在各自目录里，因为进那个目录干活的人
  第一个要读的就是它。
- **`docs/` 只放跨模块的东西**：架构、产品、领域概念、决策、计划、研究。
  它不是文档的收容所——凡是只讲一个模块的，回到那个模块里去。
- **合约跟着生产方走。** `backend/api.md` 在 backend 下而不是 docs 下，
  因为它随后端代码一起变（近 60 个提交改了 11 次）。

## `docs/` 里各目录的分工

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `decisions/` | 已经做出的技术决策：背景、备选、依据、后果。写完不改，错了就新写一条推翻它 | 计划、待办 |
| `plans/active/` | 在做的事，含在途欠账。做完移到 `completed/` | 已完成的 |
| `plans/completed/` | 做完的计划，留作对照 | — |
| `research/` | 假设预注册（`prereg/`）、裁决日志、研究收官 | 产品设计 |
| `data/` | 数据层清单、缺口、同步纪律 | — |
| `archive/` | 被取代的历史文档，文首必须写明被谁取代 | 还在用的 |

## 文档是交付物的一部分

改了行为就在同一个提交里改文档。两次文档审计各改出约 20 处失真，
成因都一样：代码变了文档没跟。

**能被机械检查的数字，就让它被检查。** 设计文档里曾长期写着「39 符号」
而实际是 90、「overrides 103 条」而实际是 77——这类数字要么别写，
要么写进测试断言。

## 注释与提交信息

写**为什么**，不写做了什么。做了什么看 diff 就行。

有实测就带上实测：「macOS 上 `time.monotonic()` 睡眠期间不走字，开发机实测
开机 9.2 天里只清醒 52%」比「用墙钟更可靠」有用得多。

踩过的坑要留在原地。被删掉的坑会被重新踩一遍。

## 冻结规范

`backend/fanisl/knowledge/` 下的 `extraction-guide.md` 与 `merge-guide.md`
是**冻结规范**：改动必须升 `extractor_version`，旧版本产出保留不删（版本化重放）。
只改填写口径、不改分级与评分语义的，可以不升版本，但要在改动里写明理由。
