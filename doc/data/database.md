## 先分类

| 数据类型                             | 策略                   | 原因                                     |
| ------------------------------------ | ---------------------- | ---------------------------------------- |
| 历史 OHLCV                           | **不存**（或仅冷归档） | API 随时可重取，囤了是冗余               |
| 资金费/OI/爆仓/多空比 快照           | **必须积累**           | 时点性、API 不给历史，今天不抓就永远丢了 |
| 情绪/恐慌贪婪/社交 读数              | **必须积累**           | 同上，瞬时值不可回填                     |
| Claude 的每次分析 + 它当时看到的快照 | **最该存**             | 完全不可重建，且是你做前向评估的唯一素材 |
| 近期 K 线 / 指标计算结果             | **缓存（短 TTL）**     | 可重取但重复拉浪费配额和延迟             |

这张表里**第二、三、四行是存储层的真正理由**，第一行不是。尤其第四行——把 Claude 每次的分析连同输入快照一起落库——是性价比最高、最该立刻做的一件事，下面会展开。

## 1. 缓存层（最先做，ROI 最高）

对话 agent 里同一个 symbol/timeframe 在一次会话内、跨用户间会被反复请求。用
**cache-aside** 模式：工具先查缓存，命中直接用，未命中才打 API 并回填。

- **TTL 对齐数据的自然更新节奏**，而不是拍脑袋：已收盘的 K 线是不可变的→可长期缓存；当前未收盘那根→短 TTL；资金费约 8h 更新→TTL 几分钟到对齐周期；OI 持续变→几分钟；恐慌贪婪日更→几小时。决策支持本来就容忍分钟级延迟，所以缓存收益很大、风险很小。
- **缓存键** = (source, symbol, endpoint, params)。
- **放哪**：你现在单进程，先用进程内 LRU +
  SQLite 落一层就够；等多进程/多用户再上 Redis。别一上来就 Redis。

## 2. 时间序列积累（只积累"拿不回来"的）

定时抓取的对象**只应是那些 API 不给历史的时点数据**：资金费、OI、爆仓、多空比、情绪读数、市场广度。别去定时抓 OHLCV。

存储选型，建议走**操作型行存 + 分析型列存的分离**（这也正好是 OLTP/OLAP 划分，对金融 IT 方向是好信号）：

- **操作型（热）**：会话、分析记录、最新快照——**继续用 SQLite**。单节点、写并发低，够用。要更"生产化"再上 Postgres。
- **分析型（冷/回测）**：积累的时序 + 回测扫描——**DuckDB +
  Parquet**。嵌入式(像 SQLite 一样无需起服务)、列存、扫海量历史飞快、直接读 Parquet、还能跨查 SQLite。对单节点的积累+回测，这是比 InfluxDB 省心、比 ClickHouse 轻的甜点选择。
- 想"一个真·服务器库统管一切"再考虑 **Postgres +
  TimescaleDB**（连续聚合、hypertable）；ClickHouse/QuestDB 更"金融 IT"但运维更重，现在是过度设计。

注意：**定时抓取一引入，就把之前砍掉的"管线"又请回来了**——但这次范围是对的：一个**后台 ingester 进程**，只负责抓取+落库瞬时数据，和对话 agent
**解耦**。agent 只管读(store-first，未命中再走 live API)，ingester 只管写。

## 3. 定时抓取的工程要点

- **调度器**：单节点用 APScheduler 或 cron 即可，别上 Celery。
- **幂等 + 去重**：用 (symbol, source, ts) 唯一约束，重复抓不产生脏数据。
- **缺口检测 + 重启回填**：进程挂了重启后，检查最后一条时间戳，补抓断档(对能补的源)；不能补的源(纯瞬时)就如实留缺口。
- **失败/限流**：退避重试；某源挂了写一条"该时点不可用"而不是静默丢，这样回测时知道是真没数据。

## 4. 回测

把回测和积累放一起说，但它是另一个量级的东西，有两类陷阱：

**通用陷阱（任何回测都有）**：点时正确性（回测时用的必须是"当时能看到的"数据，别用事后修订值）、前视偏差、幸存者偏差（退市的币/股要留在样本里）。所以积累的快照一定要带 as-of 时间戳、原样保存。

**LLM 特有的、且致命的陷阱**：如果的策略含 Claude 的判断，**朴素的历史回测是无效的**——因为 Claude 的训练数据里已经"知道"2021、2023 那些行情后来怎么走了。让它分析一段它训练时见过结局的历史，得到的不是策略表现，是污染后的后见之明。这点很多人会忽略。

所以建议是把两者**彻底分开**：

- **确定性规则回测**：纯代码规则(指标、阈值、COT 信号那种)跑在你积累的历史上——干净、有价值，DuckDB 就是为这个生的。
- **LLM 策略评估**：**别做历史回测，做前向/纸面评估**。具体就是上面第 4 行——把 Claude 每次的实时分析连同输入快照、时间戳落库，然后**向前**看它的判断在之后的真实行情里表现如何。这既绕开了训练污染，也是唯一诚实的 LLM 策略评估方式。而且它现在就能开始攒数据，攒得越早越值钱。
